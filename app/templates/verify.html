Check it yourself

set -e
base=https://links.kituwa.com

# 1. Fetch the manifest, its signature and the signing key.
curl -fsSLO $base/release.json
curl -fsSLO $base/release.json.sig
curl -fsSLO $base/release.pub

# 2. The manifest is signed with an Ed25519 key held by the operator.
openssl dgst -sha256 -verify release.pub -signature release.json.sig release.json

# 3. Download the exact artifact this server deploys and hash it.
tarball=$(python3 -c 'import json;print(json.load(open("release.json"))["tarball"])')
commit=$(python3 -c 'import json;print(json.load(open("release.json"))["commit"])')
curl -fsSLO $base/release/$tarball
sha256sum $tarball
# compare with "sha256" in release.json

# 4. Rebuild the artifact from the public commit and compare.
git clone {{ repo_url }} links-kituwa
cd links-kituwa && git checkout $commit
git archive --format=tar.gz --prefix=links-kituwa/ HEAD > ../rebuilt.tar.gz
cd .. && sha256sum rebuilt.tar.gz $tarball
# the two hashes must match

What the hash proves

  • The artifact the site serves is byte-for-byte the tree at that public commit — anyone who clones the repository can reproduce it with git archive.
  • The signature proves the manifest came from the operator's release key, not from whoever happened to be serving HTTP that day.
  • The deployed-tree hash is computed on the host from the files the app actually imports. If someone edits a file after deploying, this page changes or the hash stops matching the signed artifact.

A compromised server can lie on this page. The hash comparison above is done on your machine, not in the browser, which is why the command block exists. The strongest check is step 4: rebuild from the commit and compare.
